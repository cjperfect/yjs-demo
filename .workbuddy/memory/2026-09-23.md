### 关键决策

- **协同算法**：Yjs CRDT（无需 OT 变换、支持离线、与 ProseMirror 集成最佳）
- **编辑器**：Tiptap v2 + y-prosemirror + CollaborationCursor 扩展
- **数据库**：复用 pgvector/pg17 + Prisma，Yjs state 存 bytea，覆盖式存储不做增量追加

- **Auth**：暂不做，先用 mock 用户跑通协同闭环

### 踩坑记录（重要）

1. **pnpm catalog 配置位置**：pnpm 12 起 `onlyBuiltDependencies` 失效，改用 `allowBuilds`（在 pnpm-workspace.yaml，不在 package.json 的 pnpm 字段）
2. **nodeLinker 迁移**：pnpm 12 配置从 .npmrc 迁移到 pnpm-workspace.yaml，字段名 camelCase（`nodeLinker: hoisted`）
3. **Prisma 5 + pnpm**：默认 isolated 模式下 @prisma/client 找不到 .prisma/client，必须用 `nodeLinker: hoisted`；schema.prisma 不指定 output 让 Prisma 用默认位置（hoisted 模式下生成到 monorepo 根 node_modules/.prisma/client）
4. **tsup dual format + ESM .js 后缀**：源码 import 用 `./xxx.js` 后缀会导致 tsup bundle 时把 export 变成 `void 0` placeholder（cjs 产物里 `exports.YjsRoomManager = void 0`）。**所有 packages 的相对 import 必须去掉 .js 后缀**
5. **tsup dts plugin + monorepo**：tsup 的 dts plugin 不读项目 tsconfig 的 include，导致跨文件 import 报 TS6307。解决方案：tsup `dts: false` + 独立 `tsc -p tsconfig.dts.json`（emitDeclarationOnly）步骤
6. **Next.js + workspace 包 CSS @import**：`@import "@yjs-demo/editor/styles.css"` 在 Tailwind v4 + Next.js 下解析失败。解决方案：把 CSS 内容直接合并到 web 的 globals.css
7. **NestJS WsAdapter path 限制**：WsAdapter 的 upgrade 事件用 `pathname === wsServer.path` 精确匹配，无法处理动态路径。必须手动绑定 httpServer upgrade 事件
8. **NestJS tsconfig paths**：apps/server 的 tsconfig 加 paths 指向 packages/src 会导致 nest build 把 packages 源码也编译进 dist。解决方案：去掉 paths，依赖 packages 的 dist 产物（先 build packages 再 build server）

## 协同 awareness 崩溃 bug 修复 + README 编写

### 修复的 bug

**根因**：`YjsRoom.removeConnection` 在最后一个连接断开时只 `flushSave`，没调 `YjsRoomManager.notifyConnectionClosed`，导致房间永不销毁、awareness 脏状态残留。新连接收到 sendInitialSync 发的脏 awareness 数据，客户端 `applyAwarenessUpdate` 里 `JSON.parse` 崩（`Unexpected end of JSON input`）。

**修复**：`YjsRoom` 构造函数加 `onEmpty?: (docId: string) => void` 回调，`removeConnection` 在 `connections.size === 0` 时调用。`YjsRoomManager.getOrCreateRoom` 创建 room 时传入 `(id) => this.notifyConnectionClosed(id)`。空房间 30 秒后被 dispose。

**验证**：用固定 docId 连跑两次（中间等 35 秒让房间销毁），第二次不再崩，证明修复生效。

## UI 美化后样式失效排查（傍晚）

用户反馈美化后样式没生效。排查发现根因是 CSS 级联问题，两个坑：

**坑 1（主因）：手写 unlayered reset 覆盖 Tailwind v4 utilities**
- globals.css 里的 `* { margin: 0; padding: 0 }` 和 `a { color: inherit }` 是 unlayered 的
- Tailwind v4 所有 utilities 都在 `@layer utilities` 里
- CSS 级联规则：unlayered 样式永远赢过 layered 样式（不看 specificity）
- 结果：所有 p-*/px-*/py-*/m-*/gap-* 类被干掉（布局崩），a 上的 text-* 和 hover 变色失效
- 修复：删掉手写 reset（Tailwind preflight 已提供），html/body 基础样式移进 @layer base，自定义工具类（shadow/glass/gradient/animation）移进 @layer components
- 修复后级联顺序：theme → base → components → utilities，utilities 正常覆盖一切

**坑 2：CSS 注释里写 `p-*/gap-*` 导致注释提前终止**
- 注释中的 `*/` 是块注释结束符，`p-*/gap-*` 里的 `*/` 把注释截断
- 后续文字变裸 CSS → Turbopack 解析失败 → 页面 500
- 修复：注释里避免写 `*/` 模式（改用中文顿号或"padding 和 gap 类"）
- 顺带发现：多次编辑 globals.css 后 Turbopack HMR 会进入坏状态，需要重启 next dev

**验证方法**：curl 编译后 CSS（grep .p-5/.gap-4/.rounded-2xl 是否存在 + @layer 顺序）比看截图更准。

**教训**：Tailwind v4 项目里绝不要手写 unlayered 的元素选择器 reset；写 CSS 注释时检查内容里是否有 `*/` 字符序列。

## 协同 + awareness 失效排查与修复（傍晚）

用户反馈"没有协同上，同时修改文档的时候，看不到其他用户"。先跑 `node apps/server/test-collab.mjs`，server 端协同 100% 正常（A 写入 → B 收到 → B 追加 → A 收到），双向同步成功。问题在前端。

**根因（上一轮加登录功能引入的回归 bug）**：
- `editor-client.tsx` 里我写 `const collabUser: User = { id, name, color }` 是**每次 re-render 都构造一个新对象**（inline 字面量）
- 这个新引用传给 `<CollabEditor user={collabUser} />`
- `use-collaboration.ts` 的 `useMemo([ydoc, provider, user])` 用 user 引用做依赖，user 引用变 → 重算 extensions
- `useEditor(editor, [docId, extensions])` 看到 extensions 引用变 → **销毁重建 editor**
- 重建 editor 会断开 yjs 协同连接、awareness 重置
- awareness 重置触发 `setUsers` → re-render → collabUser 再变新引用 → 死循环

## 修复"点击新建文档页面空白"（傍晚）

用户报告点击"新建文档"按钮后页面空白。

**根因**：`apps/web/app/editor/[docId]/page.tsx` 在 `docId === "new"` 分支用 `<script dangerouslySetInnerHTML={{ __html: "window.location.href=..." }}>` 注入跳转代码——但 **React 19 在 RSC streaming 模式下不会执行通过 `dangerouslySetInnerHTML` 注入的 `<script>` 标签**。所以 server 已经 POST 创建了文档，但前端不知道跳哪，页面停在"已创建但无跳转"的空白状态。

**修复**：换成 `next/navigation` 的 `redirect()`，它会在 server 端抛 NEXT_REDIRECT 错误，被 Next.js 框架捕获后通过 RSC payload 发出 redirect 指令：
```
3c:E{"digest":"NEXT_REDIRECT;replace;/editor/doc-XXX;307;","name":"Error","message":"NEXT_REDIRECT",...}
```
客户端 router 收到这个 digest 后自动跳转到真实 docId 的 URL。**关键坑**：`redirect()` 必须放在 `try/catch` **外面**——否则它抛的 NEXT_REDIRECT 会被 catch 吞掉，跳转失效（页面空白）。

**诊断过程**：
- curl SSR HTML 看到 main 区只有"正在加载..."占位（RequireUser 守卫在 SSR 时 loading=true 早 return），但 RSC payload 末尾能看到 EditorClient 的 props（docId + docName）—— 说明 server side 渲染正常，问题在客户端
- curl 没看到 HTTP 302 / Location header（Next.js 15 RSC redirect 不发 302，而是发 200 + RSC payload 里的 NEXT_REDIRECT digest）
- 装 `agent-browser` 真实浏览器实测：登录 alice → 首页 → 点"新建" → server redirect → /editor/<realId> → 编辑器完整渲染（header + 顶栏 + 工具栏 + ProseMirror 编辑区），全 work

**改动文件**：`apps/web/app/editor/[docId]/page.tsx` —— 把 `docId === "new"` 分支的 `<script dangerouslySetInnerHTML>` 改成 `redirect()`，加注释说明 `redirect()` 必须放 try/catch 外的坑

**额外发现**（暂未修，不影响功能）：Next.js 15 dev mode 在 RSC payload 里序列化了 fetch 返回的 undici Response 对象 + 完整 `_Response` 类源代码（用于 async tracing + source map），导致 RSC payload 巨大（几十 KB）。Production build 不会出现。这对页面渲染性能有轻微影响，但不影响功能正确性。

## 修复 x-owner 中文 ByteString 报错（傍晚）

用户用中文名登录后报错 `Cannot convert argument to a ByteString because the character at index 0 has a value of 38472 which is greater than 255`。

**根因**：HTTP header 值要求 ASCII（ByteString 限制，每字节 ≤ 255），中文名（Unicode 码点 > 255）直接放进 `x-owner` header 会触发 fetch 抛错。

**链路梳理**：
- `user-provider.tsx` 写 cookie 时 `encodeURIComponent(user.name)` ✓
- server component `cookies().get(...).value` **自动 decodeURIComponent** 解码了 cookie 值 → 拿到中文名 → 直接放 header → 报错
- client component `useUser().name`（已 decode 中文名）→ 直接放 header → 同样报错

**修复（统一约定：HTTP `x-owner` header 值都用 URL-encoded owner 字符串）**：
- `apps/web/app/page.tsx` + `apps/web/app/editor/[docId]/page.tsx`：server component 读 cookie 后**再 `encodeURIComponent` 一次**才能放进 header（因为 Next.js cookies() 已 decode 过一次）
- `apps/web/components/document-list-item.tsx` + `apps/web/app/editor/[docId]/editor-client.tsx`：client 拿 `user.name` 后 `encodeURIComponent` 再放 header
- `apps/server/src/documents/documents.controller.ts`：所有 `@Headers("x-owner")` 参数走新增的私有方法 `decodeOwner(raw)`：先 `decodeURIComponent` 还原中文名（不合法 % 序列容错返回原值），再传给 service

**坑**：之前以为 cookie 直接是 URL-encoded 字符串，但 Next.js `cookies()` 已经 decode 过一次，所以 server component 必须再 encode 一次；而 client component 拿的是已 decode 的中文名，直接 encode 一次即可。两边语义不同但代码层面都是 `encodeURIComponent`。

**验证**：typecheck web + server 都零错误；后端 8 步 curl 全过（中文 owner 创建/列表/单查/隔离/协作/删除）；agent-browser 实测中文名 "陈同学" 登录后：首页正常显示空状态、点"新建文档"redirect 到 /editor/doc-XXX 编辑器完整渲染（含工具栏 + contenteditable）、回首页列表显示新建文档带 ✎/🗑 按钮。无红色错误框。

## 修浏览器 fetch 报 ERR_CONNECTION_REFUSED / Failed to fetch（晚上）

用户反馈点击"私有"切换按钮和删除文档都报 `TypeError: Failed to fetch`（Chrome 对应 `net::ERR_CONNECTION_REFUSED`），但 curl 和 node fetch 都能正常连后端 3001。

**排查过程**：
1. CORS preflight 正常（OPTIONS 返回 204 + `Access-Control-Allow-Origin/Headers/Methods` 齐全）→ 不是 CORS 问题
2. IPv4 (127.0.0.1)、IPv6 ([::1])、localhost 三种方式 curl 都返回 200 → 不是服务端问题
3. node fetch 模拟浏览器 PATCH 请求也成功（HTTP 200, isPublic: true, role: owner）→ 不是请求格式问题
4. `scutil --proxy` 发现 **系统代理开启**（Clash，HTTP/HTTPS 代理 `127.0.0.1:7897`）→ 浏览器走系统代理拦截了直连 localhost:3001 的请求；curl/node 不走浏览器代理所以正常

**根因**：浏览器使用 macOS 系统代理（Clash 代理），把 fetch `http://localhost:3001/api/...` 路由到代理服务器 127.0.0.1:7897，代理无法正确转发到 localhost:3001 → TCP 连接被拒 → `ERR_CONNECTION_REFUSED`。而 server component（page.tsx）的 fetch 在 Node.js 进程里执行（undici 不自动读 `http_proxy` 环境变量），所以不受影响。

**修复**：client component 的 fetch 改走**同源相对路径** `/api/...`，由 Next.js dev server 的 rewrites（`/api/:path*` → `http://localhost:3001/api/:path*`）在 server 端转发。浏览器只发请求到 localhost:3000（和打开页面一样的同源请求），不经代理直连 3001。
- `apps/web/app/editor/[docId]/editor-client.tsx`：`apiBase` 从 `process.env.NEXT_PUBLIC_API_URL ?? "http://localhost:3001"` 改成 `""`（空字符串），所有 `${apiBase}/api/...` 变成 `/api/...`
- `apps/web/components/document-list-item.tsx`：同上
- server component（page.tsx）不改——它的 fetch 在 Node.js 里执行，不受浏览器代理影响，继续用绝对路径

**验证**：Next.js /login 200（编译正常）；`curl http://localhost:3000/api/documents` 返回文档列表（rewrites 转发正常）。用户硬刷新浏览器后 togglePublic/submitDelete 应该正常工作。

**可复用 pattern**：当 client component fetch 到不同端口的 API 报 ERR_CONNECTION_REFUSED 但 curl 正常时，首先检查 `scutil --proxy` 看系统代理。修复方式是走 Next.js rewrites 同源相对路径，避免跨域直连。

## 修复 WebSocket 被代理拦截 + 非 owner 内容空 + 隐藏邀请按钮（晚上）

用户反馈：① 另一个用户打开协作链接内容是空的 ② 非 owner 不该有"邀请协作"按钮。

**根因 1（内容空）**：WebSocket `wsUrl` 直连 `ws://localhost:3001/yjs`，被系统代理（Clash）拦截 → 浏览器 WebSocket 连不上 → owner 编辑的 Yjs update 只在客户端本地 → 服务端 ydoc 是空的 → flushSave 存 0 bytes state → 非 owner 打开即使 WebSocket 能连也收到空内容。查数据库确认 `doc-z4S7axRNvdXM`（陈江的文档）state = 0 bytes。

**修复 1**：让 WebSocket 也走同源，通过 Next.js rewrites 代理到 3001（和 HTTP fetch 同一方案）：
- `apps/web/next.config.ts`：rewrites 加 `/yjs/:path*` → `${apiBase}/yjs/:path*`
- `apps/web/app/editor/[docId]/editor-client.tsx`：wsUrl 从 `ws://localhost:3001/yjs` 改成基于 `window.location.host` 动态拼接 `ws://${window.location.host}/yjs`（server 端 fallback `ws://localhost:3000/yjs`，CollabEditor ssr:false 只在 client 用）

**关键发现**：Next.js 15 rewrites 支持 WebSocket upgrade 代理！`ws://localhost:3000/yjs/test-proxy` 成功代理到后端 3001。

**修复 2（隐藏按钮）**：`editor-client.tsx` 的"邀请协作"按钮加 `{isOwner && (...)}` 条件，仅 owner 可见。非 owner（访客/协作者）看不到邀请入口。

**端到端验证**（走同源 `ws://localhost:3000`）：
- A 写入 → B 收到 "Hello from A via proxy" ✓
- B 追加 → A 收到 "Hello from A via proxy and B too" ✓
- 数据库 state = 67 bytes（之前 0 bytes）✓

**注意**：之前 WebSocket 断连期间 owner 编辑的内容已丢失（state 0 bytes，客户端关页面后本地 Yjs 文档也没了）。用户需重新编辑文档内容。

**教训**：HTTP fetch 和 WebSocket 是两个独立通道，修了 HTTP 同源代理后必须同时检查 WebSocket 是否也走直连。`scutil --proxy` 的系统代理会拦截所有跨端口连接，包括 ws://。

## 复制链接改用局域网 IP 替代 localhost（晚上）

用户要求"复制链接不用 localhost，用 IP 吧"——把链接发给同局域网其他设备时 localhost 无意义，需用本机 LAN IP。

**实现**：后端加端点动态返回本机 IP，前端复制时替换 localhost：
- 新建 `apps/server/src/info/info.controller.ts`：`GET /api/info/lan-ip`，用 `os.networkInterfaces()` 遍历返回第一个 IPv4 非回环地址（动态获取，不用硬编码）
- `apps/server/src/app.module.ts`：`controllers: [InfoController]` 注册（直接挂 AppModule，不用单独 module）
- `apps/web/app/editor/[docId]/editor-client.tsx` 的 `handleCopyLink`：复制前先 `fetch('/api/info/lan-ip')` 拿 IP，把 URL 中 `localhost` 替换成 IP；获取失败则用原 URL 兜底

**验证**（全部用 IP `192.168.0.100`）：
- 前端 `http://192.168.0.100:3000/login` → 200（局域网设备可访问）
- API `http://192.168.0.100:3000/api/info/lan-ip` → `{"lanIp":"192.168.0.100"}`（同源代理 work）
- WebSocket `ws://192.168.0.100:3000/yjs/ip-test` → SUCCESS（同源 WS 代理 work）

整个链路用 IP 访问完全正常：其他设备打开 `http://192.168.0.100:3000/editor/doc-xxx`，HTTP fetch 和 WebSocket 都走同源（IP:3000）由 Next.js rewrites 代理到后端 3001，不受系统代理影响。

## 再合并：apps/server/src/yjs-server → yjs（晚上）

用户问"yjs 和 yjs-server 能合并起来吗"。两个目录本质是同一模块两层实现：`yjs/` = NestJS 集成层（Prisma + 注入 + URL 路由），`yjs-server/` = 纯 Yjs 协议层（room/sync/adapter/types，不依赖 NestJS）。之前拆成独立 packages 包是为协议层可复用，已合并进 apps/server 后再保留两个目录就是冗余分层。

**方案**：物理合并（yjs-server/ 5 个文件移进 yjs/），不做逻辑融合——保留 YjsPersistence 接口的依赖倒置设计（YjsService 是 Prisma/NestJS 绑定，YjsRoomManager 是纯协议，解耦合理）。

**改动**：
1. `mv yjs-server/{types,ws-adapter,sync-handler,room,room-manager}.ts yjs/`，删 barrel `index.ts`，rmdir yjs-server
2. `yjs.service.ts`：`from "../yjs-server"`（barrel）→ 拆成 `from "./room-manager.js"`（YjsRoomManager）+ `from "./ws-adapter.js"`（createWsConnection）+ `import type { YjsPersistence } from "./types.js"`
3. 顺手统一日志前缀：`sync-handler.ts` 的 `[yjs-server]` → `[yjs]`；`types.ts` 注释 "yjs-server 包内做 debounce" → "YjsRoom 内做 debounce"
4. 清理 `dist/yjs-server` 残留死代码

**零修改点**：内部 5 个文件互相用 `./types`、`./room` 等相对引用，移动后同目录内仍然有效；`main.ts` 引用 `./yjs/yjs.service.js`（目录名 yjs 不变）不受影响；`@yjs-demo/shared` 引用不变。

**验证**：typecheck 4/4 通过；NestJS watch 自动重编译，dist/yjs/ 已有 7 个新文件，yjs.service.js import 已指向 `./room-manager.js`；server API 200、WebSocket 同源代理 SUCCESS。

**最终结构**：`apps/server/src/yjs/` 一个目录 7 个文件（yjs.module.ts、yjs.service.ts、room-manager.ts、room.ts、sync-handler.ts、ws-adapter.ts、types.ts），协议层和 NestJS 集成层同目录但职责仍清晰分离。
